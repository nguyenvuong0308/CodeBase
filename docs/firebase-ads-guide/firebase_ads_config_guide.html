Guide 1 · Luồng chuẩn

Cấu hình Firebase Ads từ đầu

Thực hiện theo đúng thứ tự dưới đây để dễ khoanh vùng lỗi. Không nên paste toàn bộ config production rồi bật ads ngay từ lần publish đầu tiên.

  1. Chọn flavor và lấy defaults làm baseline

    Dùng app/src/dev/res/xml/remote_config_defaults.xml khi debug và app/src/prod/res/xml/remote_config_defaults.xml khi release. Defaults ở core/config/src/<flavor>/res/xml là baseline của module; resource phía app có thể override khi merge.

  2. Tạo parameter đúng kiểu trên Firebase Console

    Các object/array JSON phải tạo dưới kiểu String. Chỉ is_turn_on_ad_places_disabled_when_detect_test_ad dùng kiểu Boolean. Key động ad_place_ab_<place_name> cũng là String.

  3. Cấu hình công tắc và chính sách toàn app

    Bắt đầu với application_config, country block, test-ad protection, consent và click protection. Giữ is_enable_ads=false nếu chưa sẵn sàng kiểm thử ad unit thật.

  4. Khai báo ba danh sách ad place

    Đặt banner/native vào banner_native_ad_places, app open vào app_open_ad_places, fullscreen vào rewarded_rewardedinter_inter_ad_places. Mỗi object cần tối thiểu place_name, ad_id, ad_type, is_enable.

  5. Thêm config global theo loại quảng cáo

    Thiết lập retry, interval, timeout, TTL và behavior trong *_ad_config. Global config không thay thế field nhận diện của từng place.

  6. Validate, publish có điều kiện và smoke test

    Validate JSON, dùng Firebase condition/experiment nếu rollout hạn chế, publish rồi force fetch trên debug. Kiểm tra log, consent, load/show/dismiss và fallback khi mất mạng.

Quy tắc kiểu dữ liệu: Firebase Console không có kiểu JSON riêng cho luồng này. Hãy lưu JSON object/array dưới dạng String hợp lệ; không thêm comment, dấu phẩy cuối hoặc dùng single quote. JSON lỗi sẽ khiến model về default nội bộ; riêng list ad place lỗi/rỗng sẽ tiếp tục fallback sang key kế tiếp.

Thứ tự resolve thực tế

Firebase defaults (theo flavor)
        ↓ fetchAndActivate()
Remote Config value đã activate
        ↓ parse bằng Moshi / primitive getter
versioned ad-place key (khớp versionCode và list không rỗng)
        ↓ nếu không dùng được
fallback key *_2 (list không rỗng)
        ↓ nếu không dùng được
default ad-place key
        ↓
A/B override toàn object (nếu hợp lệ)
        ↓
Mapper → cache → AdsManager

Checklist trước khi publish

  • Key khớp chính xác với bảng parameter
  • JSON parse được và không có trailing comma
  • place_name không trùng trong các list
  • ad_type đúng nhóm và đúng enum hỗ trợ
  • Ad unit ID đúng loại quảng cáo
  • Đã test cả fetch thành công và fallback defaults
  • Debug consent chỉ chứa test device
  • Rollout production có condition/experiment phù hợp
Nguồn logic: RemoteConfigService gọi setDefaultsAsync(R.xml.remote_config_defaults) và fetchAndActivate(). RemoteConfigRepositoryImpl parse, map và cache config; các AdsManager đọc dữ liệu đã resolve từ repository.

Replace các key *_2 từ app module

banner_native_ad_places_2app_open_ad_places_2rewarded_rewardedinter_inter_ad_places_2

Không cần sửa ConfigParam.kt trong core. Mở app/src/main/java/com/codebasetemplate/required/firebase/AppAdPlacesRemoteConfigKeyProvider.kt và thay giá trị của key cần dùng riêng cho app:

class AppAdPlacesRemoteConfigKeyProvider @Inject constructor() :
    AdPlacesRemoteConfigKeyProvider {
    override val bannerNativeAdPlacesKey = "my_banner_native_ad_places"
    override val appOpenAdPlacesKey = "my_app_open_ad_places"
    override val rewardedRewardedInterInterAdPlacesKey =
        "my_rewarded_inter_ad_places"
}

Provider của app đã được đăng ký vào Hilt trong RequiredModule. Khi tạo app module mới hoặc di chuyển implementation, giữ binding @IntoSet sau:

@Provides
@IntoSet
@Singleton
fun provideAdPlacesRemoteConfigKeyProvider(
    provider: AppAdPlacesRemoteConfigKeyProvider,
): AdPlacesRemoteConfigKeyProvider = provider
Thứ tự resolve: key theo ad_places_version_config được đọc trước. Nếu không có dữ liệu hợp lệ, core đọc key *_2 do app provider cung cấp, rồi mới fallback về banner_native_ad_places, app_open_ad_places hoặc rewarded_rewardedinter_inter_ad_places. App có thể chỉ override một property; các property còn lại tự dùng key mặc định của core.

A/B testing theo ad place

ab_testing_ad_place_namesad_place_ab_<place_name>

Cơ chế A/B testing hoạt động như một lớp override đặt trên các list ad place hiện tại. Core resolve list gốc theo thứ tự versioned key, key *_2 và key mặc định trước; sau đó mới áp dụng override. Việc replace diễn ra hoàn toàn trong core:config, vì vậy app tiếp tục dùng getAdPlaceBy(...) và AdsManager như cũ, không cần sửa implementation.

1. Khai báo danh sách place được A/B test

ab_testing_ad_place_names

Tạo parameter ab_testing_ad_place_names với kiểu String và giá trị là JSON array. Chỉ nên khai báo các place_name đã tồn tại trong một trong ba list ad place gốc.

[
  "anchored_bottom_home",
  "fullscreen_test"
]

2. Tạo parameter override cho từng place

ad_place_ab_<place_name>

Tên parameter tuân theo format ad_place_ab_<place_name>. Ví dụ với place anchored_bottom_home, parameter tương ứng là:

ad_place_ab_anchored_bottom_home

Giá trị control/default có thể để rỗng. Giá trị variant phải là một object ad place đầy đủ; tối thiểu phải có place_name, ad_id, ad_type và is_enable.

{
  "place_name": "anchored_bottom_home",
  "ad_id": "ca-app-pub-xxx/yyy",
  "ad_type": "native",
  "native_template_size": "medium_cta_bottom",
  "is_enable": true,
  "is_tracking_click": true,
  "background_color": "#FFFFFF",
  "primary_text_color": "#1F2937",
  "body_text_color": "#6B7280",
  "background_cta": "#5E56F5"
}
Quan trọng: override thay thế toàn bộ object, không merge từng field. Mọi field không xuất hiện trong variant sẽ nhận default của mapper, không giữ giá trị từ object gốc. Vì vậy hãy copy object gốc rồi sửa các field cần test.

3. Thiết lập experiment trên Firebase

  1. Giữ ab_testing_ad_place_names là parameter chung, không cần thay đổi giữa control và variant.
  2. Chọn ad_place_ab_<place_name> làm parameter của experiment.
  3. Control dùng chuỗi rỗng để app giữ nguyên object trong list gốc.
  4. Variant dùng JSON object đầy đủ muốn thử nghiệm.
  5. Publish Remote Config và chạy experiment theo phân bổ user của Firebase.

Quy tắc resolve và fallback

  • Danh sách tên được trim, loại phần tử rỗng và loại trùng.
  • Override chỉ áp dụng cho place đã có trong list gốc; không thể thêm place mới.
  • place_name trong object override phải trùng chính xác với tên nằm trong danh sách.
  • Key không tồn tại, value rỗng, JSON lỗi hoặc thiếu field bắt buộc sẽ giữ nguyên object gốc.
  • Thứ tự và số lượng phần tử của list gốc không thay đổi.

onboarding_config

core:startflow giữ logic điều hướng, quảng cáo và tracking. App custom nội dung/giao diện qua các API mở rộng, không cần copy layout hoặc sửa code trong module core.

APIVai tròLưu ý
OnBoardingContentProviderCung cấp số trang, ảnh, title và subtitle.Chỉ nên đăng ký một provider; nếu không có sẽ dùng nội dung mặc định.

Cung cấp content

@Singleton
class AppOnBoardingContentProvider @Inject constructor() : OnBoardingContentProvider {
    override val introPageCount = 3

    override fun getImageResIntro(position: Int) = when (position) {
        0 -> R.drawable.intro_1
        1 -> R.drawable.intro_2
        else -> R.drawable.intro_3
    }

    override fun getStringIntro(position: Int) = when (position) {
        0 -> R.string.onboarding_title_1
        1 -> R.string.onboarding_title_2
        else -> R.string.onboarding_title_3
    }

    override fun getSubtitleIntro(position: Int): Int? = when (position) {
        0 -> R.string.onboarding_subtitle_1
        1 -> R.string.onboarding_subtitle_2
        2 -> R.string.onboarding_subtitle_3
        else -> null
    }
}

getSubtitleIntro() được UI V2 và card top_v2 của V3 sử dụng; trả về null để ẩn subtitle.

Custom bằng UiSpec hoặc thay toàn bộ page

@Singleton
class AppOnBoardingV3UiCustomizer @Inject constructor() : OnBoardingV3UiCustomizer {
    override fun customize(
        context: Context,
        state: OnBoardingV3PageState,
        current: OnBoardingV3UiSpec,
    ) = current.copy(
        actionText = context.getString(
            if (state.isPageEnd) R.string.onboarding_start else R.string.onboarding_next
        ),
        actionBackgroundRes = R.drawable.bg_onboarding_primary_button,
    )
}

V1/V2 dùng cùng mô hình qua OnBoardingV1UiCustomizer/OnBoardingV2UiCustomizer. V2 UiSpec có thêm isActionFillGradientEnabled và actionFillGradientColors.

App đặc thù implement OnBoardingV1/V2/V3PageRenderer tương ứng, inflate layout app với scope.parent và false, rồi gọi scope.actions.onPrimaryAction(). Với V3, forward onBannerNativeResult vào ad container của layout app. Không override XML của core bằng resource cùng tên.
